- Status: Accepted; contracts unfrozen until v0.1 (ADR 0019)
- Date: 2026-10-02; dispatch moved into v1 on 2026-10-03 ([ADR 0025](../adr/0025-v1-includes-dispatch.md))
- Part of: [02b](02b-hub-api.md), [02j](02j-hub-runtime.md)
- Inputs: [`service.proto`](../../api/fleet/hub/v1/service.proto), [`watch.proto`](../../api/fleet/hub/v1/watch.proto),
  [01](01-agent-capabilities.md) (the v1 and v3 tags), the [v1 plan](../plan/v1-implementation-plan.md)
- Authority: the protos define each message; this file says which release serves
  it and which plan PR builds it. When it disagrees with a proto, the proto wins.

The plan builds the hub API's RPCs and Watch topics in two releases, v1 and
v3; the count line under each table below gives the totals. There is no v2: it was
merged into v1 by ADR 0025. This file is the one list, so a PR that adds an RPC can say where
it belongs and a reader can tell "not built yet" from "forgotten".

## Out-of-release behaviour

- An RPC the running build does not serve yet (a v3 RPC, or a v1 RPC whose plan
  row has not landed) answers gRPC `UNIMPLEMENTED`
  (Connect `unimplemented`). The hub registers every handler of the service so a
  client built from a newer proto gets this answer, not a connection error.
- A `Watch` topic the running build does not serve is refused as a whole subscription
  with `INVALID_ARGUMENT` and the topic named. It is never silently empty.
- `GetServerInfoResponse.features` lists exactly what is served (`attach`, `routines`,
  `devices`, `watch.pane_summaries`, and so on). Clients hide what is not listed.
- A `fleetd.yaml` key whose feature has not landed is in one of two lists below,
  never silently ignored ([02j](02j-hub-runtime.md#configuration-file)).
  **Refused at start with "not built yet":** `mode: authenticated` and the
  authenticated-mode keys `public_hosts`, `public_origins`, `tls.api_cert_file`,
  `tls.api_key_file`, `tls.api_tailscale` (v3); `listen.pprof` (no plan row builds
  it yet); `telemetry.otlp.endpoint` (until OTLP export lands).
  **Loaded and checked, no effect until the row that uses it:** `rate_limits.*` (row 12, the per-principal and
  per-peer limits, `/metrics` included); `timing.max_sync_lag` (rows 13 and 23);
  `timing.verify_grace` (row 22); `timing.ready_timeout` and
  `timing.goal_file_timeout` (row 21); the `github` section (row 11; its key files
  are never opened before then); the other `telemetry.otlp` keys (with the
  endpoint).
- Sign-in and device RPCs in `local_trusted` stay `FAILED_PRECONDITION`
  ([02f](02f-hub-authentication.md#modes)); that is a mode rule, not a release rule.

## Commands of the three programs

Exit codes are 0 for success, 1 for a command that ran and failed, and 2 for bad
usage (an unknown command or flag, or an extra argument), the way the cobra
commands of all three programs report it (ADR 0020). `--json` prints
the Connect JSON of the response message unchanged: field names as protobuf
writes them in JSON, enum names in full, 64-bit integers as decimal strings
([02b](02b-hub-api.md#64-bit-integers)). `fleet status` prints one object,
`{"summary": <GetFleetSummary>, "system": <GetSystemStatus>}`. The golden files
of plan PR 15 fix these shapes. `FLEET_URL` names the hub; `FLEET_TOKEN` is
optional in `local_trusted` (a valid token only narrows the owner's scopes, 02f).
Destructive commands need `--yes`.

| `fleet export`, `fleet import [--dry-run]` | `fleet.yaml` out and in | `ExportConfig`, `ImportConfig` | v1 (15) |

until re-enroll exists (later in row 4, and row 13a's `previous_machine`) an enrolled machine is refused, never re-enrolled over: remove only `identity.json` (and `enroll.key` if present) and keep `agent.db`, which holds `install_id`, and the next enroll removes `cert.pem` and `renew.key`, the old identity's renewed certificate; a stray argument is refused without being echoed; exit 0, 1 on failure, 2 for bad usage), run the agent (`run`: takes `<state-dir>/fleet-agent.lock`, a second `run` on the folder exits 1; connects to the cached address, then the hub found by one mDNS browse, then the hub's latest address list (`hub-addresses`, else the enrolled one) over mTLS and stays connected, renewing its certificate at two thirds of its life into `cert.pem` without touching `identity.json` ([02g](02g-agent-security.md#certificate-renewal-a4)); exits 0 on SIGTERM or SIGINT after `Bye{SHUTDOWN}` (and on one during startup, a clean stop unless a real failure came with it), 1 when not enrolled or when the loop ends on its own: revoked, unknown machine, another fleet, certificate expired (the one that ends last, enrolled or renewed); the first three are saved in `ended.json`, so a later `run` exits 1 before any network call, naming the fix, until the machine is enrolled again (enroll removes the file) or the owner removes it; a damaged `ended.json` also makes `run` exit 1 before any network call, saying to remove the file; logs go to stderr; `run` makes the config folder (mode 0700) when it is missing, loads and watches `policy.yaml` there ([03e](03e-settings-and-drift.md#the-local-policy-file-l1-policyyaml)) and never writes it; it sends each policy change and each resource sample to the hub as events, keeping the policy change in `agent.db`'s event ring until the hub holds it ([02i](02i-delivery-and-sequencing.md)); `enroll` also takes `--repos <dir>` (asked for on a terminal when not given, before any network call) and writes the starter `policy.yaml`, never over an existing one); with a tmux on the path or in Homebrew's or the system's folder, `run` watches the tmux socket folder (01 E2, defaults) and keeps one control client on the `default` and `fleet-probe` servers there, reporting their sessions, windows and panes ([01](01-agent-capabilities.md) E1 to E3); it only reads tmux, never sets an option or types a key; with tmux present `run` also starts the goals-and-repos observer (row 9: the refresher rebuilds the checkout table and forge state, the tracker attributes goal files and emits GoalState events, repos and goals ride every Snapshot, and the tracker re-reads goal panes for harness conditions (01 E12: open and cleared HarnessCondition events, open ones in Snapshot.conditions); without tmux there is nothing to attribute and the Snapshot carries none); `run` keeps `status.json` current and `enroll` leaves a failed enroll's code in `enroll.json`, both in the state folder for `doctor`: [03 W1](03-workflows.md#persistence)); `--state-dir` (default `~/.local/state/fleet-agent/`); `--config-dir` (default `~/.config/fleet-agent`, or `$XDG_CONFIG_HOME/fleet-agent`) | `Enroll`, `Connect`, `RenewCert` | v1 (4, 6) |
| `fleet-agent doctor` | every local check with a reason, including the hub handshake (a TLS handshake against the pinned CA, never a `Connect` call), the push socket and the last mDNS browse, probe-folder trust and Linux linger (`--json` prints one object; each check is `ok`, `warn`, `fail`, `unknown` or `not_checked`, `not_checked` naming the row that adds it; it reads `status.json`, `enroll.json`, `ended.json` (read-only, as `run` reads it: it says the agent will not reconnect only from this file, or from an expired certificate), `policy.yaml` and the certificate dates fresh, never `agent.log`, `agent.db` or a key, and changes nothing except the probe-trust look (each installed harness starts once in the probe folder on a throwaway tmux server, the first screen is read, no key is sent and the session is torn down, [01](01-agent-capabilities.md)); a `policy.yaml` or config folder that every user may write is a `fail`, one that only its group may write is a `warn` ([03e](03e-settings-and-drift.md#the-local-policy-file-l1-policyyaml)); exit 0 unless a check is `fail`, then 1) | local | v1 (6) |
| `fleet-agent upgrade`, `fleetd upgrade` | fetch the next GitHub release, check its checksum, swap the binary ([02j](02j-hub-runtime.md#install-and-upgrade)) | local | v1 (16) |
| `fleet-agent hook`, `hooks uninstall`, `drain`, `undrain`, `approve`, `deny` | goal hooks, local drain, local approval | local | v1 (20, 24, 18) |

`fleet backup` in ADR 0002 means `fleetd backup`. In v1 `fleet` and the dashboard
run on the hub machine (`local_trusted` binds loopback). From another machine,
forward the port over SSH with the same port number on both sides
(`ssh -L 7080:127.0.0.1:7080 <hub>`); a different local port would send a
`Host` header the hub refuses (`HOST_NOT_ALLOWED`, [02f](02f-hub-authentication.md)).
From v3 `fleet` runs on any machine that can reach the API (`authenticated`).

## Labels that change behaviour

A label is free text the owner or the local policy adds ([03e](03e-settings-and-drift.md)).
Only these two are read by the hub:

| Label | Effect | Where |
|---|---|---|
| `always-on` | first choice for a usage probe; its absence for over 10 minutes raises the `AGENT_CONNECTED` System item | [03b](03b-usage-and-sync.md), [05b](05b-observability.md) |
| `laptop` | ranked below a machine without it when placing a probe | 03b |

## The test seed

PRs 12 to 15, 28 and 29 test against one **seed package**, built in PR 12: it replays a
recorded agent stream (captured from the PR 5 fake agent) into a real hub store
under `testdata/`, and is versioned with the protos. The Playwright smoke per
view, the golden CLI output and the contract tests all start from it.
