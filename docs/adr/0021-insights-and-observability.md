# 0021. Insights from the fleet's own data, and observability of the fleet itself

- Status: Accepted
- Date: 2026-10-02
- Deciders: linuxdynasty

## Context

fleet-board already stores what each goal did, what each subscription had left
at every probe, and every triage item. The owner wants three things from that:
**insights** like the ones Claude gives about its own usage (is the subscription
used before it resets, which harness and model finish work, where does work get
stuck), a **written** summary now and then, and **observability of fleet-board
itself**. Constraints: development cost stays low, nothing may spend API money,
and the product must not need a collector, Prometheus or any other service to be
understood (ADR 0001).

## Options

1. **Ask a model through an API for the summaries.** Easy, but it is API spend,
   which the owner excluded, and it would need an API key the product does not
   hold (principle 1).
2. **Compute everything with a model.** Costly and not reproducible.
3. **Compute numbers deterministically, add rule-based suggestions, and let a
   subscription harness write the prose from the numbers.** Cheap, the numbers
   are checkable, and the only spend is subscription quota that would be wasted.
4. **Observability only through a collector.** Standard, but a self-hosted tool
   that needs a collector to show its own health fails the zero-service rule.

## Decision

**1. Deterministic rollups first.** The hub computes insights from `state.db`
with no model: subscription efficiency per account and window, goal outcomes by
harness, model, repo, account, machine and size, where work gets stuck, size
estimate versus actual, routine outcomes. Daily rows, one hourly job, one year
of retention, recomputable from source rows where the source is kept (goals,
runs, readings) and kept as the record where it is not (triage items). Two
fields are added at the sources so the numbers exist: `PromptDetected.prompt_class`
and `GoalStatus.effective_model`.

**2. Suggestions are rules, not a model.** A closed list of rules over the
rollups, each with its evidence numbers; always listed, optionally also a
low-severity (INFO, never notified) triage item. A suggestion advises; it never
changes a setting and never proposes auto-answering a prompt.

**3. The written report is a routine on a subscription.** A built-in weekly
routine runs as a normal goal (03i): the hub exports a numbers-only stats bundle
into a scratch directory the agent owns, the harness writes `report.md`, the hub
reads it back, scrubs and stores it. It runs only on spare quota (behind pace,
idle while behind, or quota that would be unused) and never into the reserve,
never on an API-key account, and the owner can disable it. Its cost is measured
and shown. **No LLM API is called anywhere in the product.**

**4. The report is untrusted text.** It is generated by a model from data that
carries no free text, but it is still model output: it is scrubbed before it is
stored and rendered as sanitized markdown (no raw HTML, no images, links as
text). Machines and accounts are aliased in what the model sees.

**5. A small agent-wire addition carries it.** `EnsureScratch` and
`CollectScratch` (capability `scratch`), a `WORKTREE_MODE_SCRATCH` goal, and the
done rule `REPORT_COLLECTED`. The hub sends a goal id and bare file names, never
a path; the agent derives the directory and never follows a link. This is the
only new way the hub reads a file an agent wrote, and it reads one named file of
at most 64 KiB.

**6. Observability works with no services.** JSON logs to stderr, a Prometheus
`/metrics` on the hub, trace ids in logs and on the wire, and the System section
and triage feed inside the product. OTLP export to a collector is opt-in, set in
local configuration only (no config push), with the secret in an environment
variable. Telemetry is bounded and drops under pressure; it never blocks the
writer.

**7. `/metrics` and pprof are guarded.** `/metrics`: a loopback peer or an
`ADMIN` API token; never a cookie or a device. pprof: off by default, a separate
loopback listener, and `ADMIN`.

**8. Agent health reaches the hub through the heartbeat.** `AgentHealth` is
added to `Heartbeat` (ring, unacknowledged results, reconnects, memory, tmux
control, probes failing, refusals); the hub exports each agent's health as
`fleet_hub_agent_*` so one scrape of the hub shows the fleet. Agent log text
stays on the machine.

**9. A System health model with a triage kind.** Ten signals with fixed
thresholds (agent connected, probe freshness, sync lag, writer lag, outbox
backlog, Watch drops, log store usage, disk free, clock skew, backup age) are
evaluated every 15 seconds and exposed by `GetSystemStatus` (READ). A signal that
leaves OK raises one **deduplicated** `TRIAGE_KIND_SYSTEM` item whose severity
follows its state, with hysteresis so it does not flap.

**10. Contract status.** Unfrozen until `v0.1` (ADR 0019): the additions
(`insights.proto`, `insights_stuck.proto`, `suggestion.proto`,
`insight_report.proto`, `system.proto`, `command_scratch.proto`, and fields in
existing messages) are free to change; `buf build` and `buf lint` pass.

## Consequences

- No new service and no new required dependency. ADR 0020's OTEL line gains the
  OTLP trace and metric exporters (stable v1, opt-in); the Prometheus exporter
  and the slog bridge stay v0 and pinned.
- The hub gains one housekeeping job, a handful of rollup tables (about 35 MB a
  year at A50 by the stated upper bounds; not yet measured) and six RPCs, all
  `READ` except `DismissSuggestion` (`APPROVALS`). Reports, rollups and
  suggestions are numbers or model text; nothing is terminal text.
- The report costs subscription quota, a few points a week by estimate
  (unmeasured until the first run), taken only from quota that would be unused.
- Stored model text is readable with `READ`. The owner may move it behind `LOGS`
  with one line in 02d if the scrubbed, numbers-derived text is judged too open.
- An old agent without capability `scratch` cannot run the report; the routine
  finds no fit machine and waits.
- The implementation proves the cost claims with a benchmark at A50 volumes and
  proves each signal with a seeded table test (fleet-performance-rigor,
  fleet-telemetry-coverage).

## Open questions

1. Report default on from first start, or off until enabled?
2. `READ` or `LOGS` for report text?
3. Real repo names to the model, or aliased?
4. `/metrics` by `ADMIN` token: accept, or add a narrower metrics scope later?
5. Thresholds fixed in v1, or owner settings?
